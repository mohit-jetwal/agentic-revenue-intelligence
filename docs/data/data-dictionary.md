# Data Dictionary

Gold-layer tables. Generated by `uv run ari generate-data`, written to
`data/local/gold/` (git-ignored). Small CSV extracts of every table are committed
under [data/sample/](../../data/sample/) so the shapes are browsable without
generating anything.

**Grain note.** The modelling grain is `product × store × day`. A separate
transaction-grain table exists for customer-level analysis, derived by
disaggregating a sample of panel rows — see [simulation-design.md](simulation-design.md).

---

## Facts

### `sales_daily` — *the primary modelling table*

One row per product × store × day. Partitioned by month.

| Column | Type | Description |
|---|---|---|
| `date` | date | Calendar day |
| `product_id` | string | FK → `products` |
| `store_id` | string | FK → `stores` |
| `channel` | string | Store channel, denormalised to avoid a join in hot paths |
| `units` | int32 | **Observed** units sold — censored by availability |
| `regular_price` | float | Undiscounted shelf price |
| `selling_price` | float | Price actually paid = regular × (1 − discount) |
| `discount_percentage` | float | 0–100 |
| `revenue` | float | `units × selling_price` |
| `cost` | float | `units × unit_cost` |
| `gross_profit` | float | `revenue − cost` |
| `promotion_id` | string \| null | FK → `promotions`; null when not promoted |
| `promotion_flag` | bool | Convenience flag for `promotion_id IS NOT NULL` |
| `inventory_available` | int32 | Opening + received on that day |
| `stockout_flag` | bool | Demand exceeded availability |

> `units` is what the till recorded, **not** what customers wanted. When
> `stockout_flag` is true the two differ, and the difference is the whole point
> of Scenario D. True demand is in ground truth and is not queryable.

### `sales_transactions`

Basket grain, derived from a sample of `sales_daily`. Partitioned by month.

| Column | Type | Description |
|---|---|---|
| `transaction_id` | string | Unique |
| `date`, `product_id`, `store_id` | — | As above |
| `customer_id` | string | FK → `customers`; drawn per the store's segment mix |
| `units` | int32 | Units in this basket |
| `regular_price`, `selling_price`, `discount_percentage` | float | As above |
| `revenue`, `cost`, `gross_profit` | float | Basket-level |
| `promotion_id` | string \| null | As above |
| `channel` | string | As above |

Units sum back exactly to the panel rows they were derived from.

### `pricing`

Daily price path per product × store. Partitioned by month.

| Column | Type | Description |
|---|---|---|
| `date`, `product_id`, `store_id` | — | Grain |
| `regular_price` | float | Shelf price |
| `selling_price` | float | After promotional discount |
| `discount_percentage` | float | 0–100 |
| `price_change_flag` | bool | True on days the regular price moved |
| `price_change_reason` | string | `scheduled` · `cost_passthrough` · `randomised_test` · `none` |

> `price_change_reason = randomised_test` marks **exogenous** price variation.
> That subset is the clean identification set for elasticity — on it, even a
> simple estimator is unbiased.

### `inventory`

| Column | Type | Description |
|---|---|---|
| `date`, `product_id`, `store_id` | — | Grain |
| `opening_inventory` | int32 | Stock at start of day |
| `received_units` | int32 | Deliveries landed |
| `sold_units` | int32 | Equals `sales_daily.units` |
| `closing_inventory` | int32 | `opening + received − sold`, exactly |
| `inventory_days` | float \| null | Days of cover at current rate; null when no sales |
| `stockout_flag` | bool | Demand exceeded availability |

### `competitor_pricing`

Product × competitor × day. Market-level, not per store — competitive
intelligence in CPG arrives as market price feeds.

| Column | Type | Description |
|---|---|---|
| `date`, `product_id` | — | Grain |
| `competitor_id`, `competitor_name` | string | Competitor identity |
| `competitor_product_id` | string | Their SKU code |
| `competitor_price` | float | List price |
| `competitor_discount` | float | 0–100 |
| `competitor_promotion_flag` | bool | On promotion |
| `competitor_effective_price` | float | After their discount — **use this** for analysis |

### `promotions`

One row per promotion event (product × store × window).

| Column | Type | Description |
|---|---|---|
| `promotion_id` | string | Unique |
| `product_id`, `store_id` | string | Scope |
| `promotion_type` | string | Price Discount · BOGO · Bundle · Display · Coupon · Loyalty Offer |
| `start_date`, `end_date` | date | Inclusive |
| `duration_days` | int | |
| `discount_percentage` | float | Depth |
| `display_flag`, `bundle_flag` | bool | Mechanics |
| `promotion_channel` | string | In-store · Digital · Both |
| `region` | string | Store's region |
| `promotion_units` | int | Units sold during the event |
| `promotion_spend` | float | Fixed cost + per-unit cost × units |

### `trade_promotions`

Retailer-level plans. The table Step 7 optimises over.

| Column | Type | Description |
|---|---|---|
| `trade_promo_id` | string | Unique |
| `retailer`, `product_id`, `region` | string | Scope |
| `start_date`, `end_date` | date | |
| `planned_spend`, `actual_spend` | float | Actuals diverge from plan, as they do |
| `expected_uplift`, `actual_uplift` | float | Fractional |
| `margin` | float | Product margin |
| `roi` | float | Incremental profit ÷ actual spend. **Below 1.0 for some rows by design** |

### `commodity_costs`

Input cost index per category per day.

| Column | Type | Description |
|---|---|---|
| `date`, `category` | — | Grain |
| `cost_index` | float | ~1.0 baseline, mean-reverting random walk |

> This is the **instrument** for price in a 2SLS specification: it shifts price
> through pass-through but does not enter demand directly.

### `sales_weekly` / `sales_monthly`

Pre-aggregated `product × store × period` rollups: `units`, `revenue`, `cost`,
`gross_profit`, `promo_days`, `stockout_days`, `days`, `avg_selling_price`.
Precomputed because "monthly revenue by region" is the single most common query
shape and re-scanning millions of daily rows for it is wasteful.

## Dimensions

### `products`

`product_id`, `product_name`, `brand`, `category`, `subcategory`, `pack_size`,
`unit_cost`, `base_price`, `launch_date`, `discontinue_date`, `product_status`
(`Active` · `Launched` · `Discontinued`).

### `stores`

`store_id`, `store_name`, `store_type`, `channel`, `region`, `state`, `city`,
`store_size_sqft`, `opening_date`.

### `customers`

`customer_id`, `segment`, `region`, `loyalty_tier`, `acquisition_channel`,
`customer_since`. **No PII** — no names, addresses or contact details.

### `calendar`

`date`, `day`, `week`, `month`, `quarter`, `year`, `day_of_week`, `day_name`,
`week_of_year`, `day_of_year`, `weekend_flag`, `holiday_flag`, `holiday_name`,
`festival_flag`, `festival_name`, `season`, `financial_month`,
`financial_year`, `financial_quarter`.

Indian financial year (April = month 1). Festival dates are the observed lunar
dates and move year to year — Diwali 2023-11-12, 2024-11-01, 2025-10-20 — with
the six days *before* each also flagged, because shoppers buy ahead.

### `product_relationships`

| Column | Type | Description |
|---|---|---|
| `product_a` | string | The product whose **demand** responds |
| `product_b` | string | The product whose **price** moves |
| `relationship_type` | string | `substitute` · `complement` · `unrelated` |
| `relationship_strength` | string | `strong` · `moderate` · `weak` · `none` |
| `cross_elasticity` | float | ∂log(demand_a) / ∂log(price_b) |

**Sign convention:** positive ⇒ substitutes (b dearer, a sells more); negative ⇒
complements. Relationships are directional and asymmetric — a premium SKU losing
volume to a value SKU is not matched in size by the reverse flow.

`unrelated` rows are labelled negatives, included so Step 9 can be scored on
false positives. A cross-price model that finds relationships everywhere is
worse than useless, and without labelled negatives there is no way to measure it.

## Not queryable: `ground_truth/`

Hidden simulation parameters, written to `data/local/ground_truth/`. **No
repository method and no SQL can reach them** — only gold tables are registered
as views. They exist solely for tests and the validation report.

| File | Contents |
|---|---|
| `elasticity.json` | True own-price elasticity per product |
| `cross_elasticity.json` | True cross-price coefficients |
| `promotion_uplift.json` | Response curve `a`, `b` per product × promotion type |
| `competitor_sensitivity.json` | True `γ` per product |
| `scenario_config.json` | Scenarios A–J with exact products, stores, windows, expected direction |
| `metadata.json` | Seed, config hash, confounder strengths in force |
| `latent_demand/` | **True uncensored demand** per product × store × day |

## Bronze layer

`data/local/bronze/` mirrors gold with deliberate corruption injected — missing
foreign keys, duplicates, invalid prices, negative quantities, out-of-range
discounts, orphan promotion ids, malformed dates. Rates are configured per
profile and the exact counts are recorded in `manifest.json`.

Gold stays pristine so Steps 4–11 are not fighting nulls in every model; bronze
gives the quality framework real defects to catch. Bronze dates are stored as
**text**, as a raw landing zone would — a typed date column physically cannot
hold `"0000-00-00"`, which is precisely why real bronze layers keep dates as
strings and let Silver parse them.

## `manifest.json`

`dataset_version`, `scenario_version`, `profile`, `seed`, `config_hash`, date
range, generation time, scenario count, row counts, partition counts, and the
injected data-quality tallies.

`LocalDataRepository.dataset_version()` reads this, so every future `ToolResult`
can be traced to the exact seed and configuration that produced the data behind
it.
